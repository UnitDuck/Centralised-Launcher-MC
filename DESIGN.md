# Centralised Launcher for Minecraft

Design recorded on 26 November 2026. This document captures the first-release requirements, the proposed implementation, and the checks that will decide whether the launcher is ready for the friend group.

## What the first release should do

One admin maintains one Minecraft Java Edition instance. Friends install the launcher, paste a reusable invite code, choose a username or an account, and click **Play**. The launcher installs and keeps the instance in sync. The admin publishes changes from the launcher and can restore the last working pack if a release breaks.

- Support Windows and macOS. Linux can wait until someone needs it. Check which Mac architectures the group uses and test the relevant builds on real machines.
- Start with the latest stable Minecraft Java Edition and prefer Fabric. On 26 November 2026, the candidate was **Minecraft Java 26.3 with Fabric**. At setup time, check the latest stable game again and verify that Fabric Loader, the required mods, and the server work together. Choose exact versions when publishing. If a required mod lags behind, tell the admin and let them decide whether to wait, replace the mod, or temporarily use an earlier stable version. [Minecraft release notes](https://www.minecraft.net/en-us/article/minecraft-java-edition-26-3) · [Fabric game version metadata](https://meta.fabricmc.net/v2/versions/game)
- Base the fork on PineconeMC (formerly ElyPrismLauncher) release `11.1.2`, commit `ac99ad44ef98dd73dd9626c7b2b668dd8cbd5c`. Reuse its instance model, Minecraft and loader installation, Java runtime handling, and existing account flows where possible. Preserve applicable upstream licensing and notices in distributed builds. [PineconeMC 11.1.2 release](https://github.com/ElyPrismLauncher/Launcher/releases/tag/11.1.2) · [Pinned commit](https://github.com/ElyPrismLauncher/Launcher/commit/ac99ad44ef98dd73dd9626c7b2b668dd8cbd5c)
- Spend $0 on pack hosting and launcher distribution for the first release. Minecraft game access and hosting the actual multiplayer server are separate from this budget and launcher feature. The existing `UnitDuck/Centralised-Launcher-MC` repo remains the source repo. The proposed distribution design uses a separate public GitHub repo for encrypted pack files.

## Per-user installation and storage

Install the launcher inside the current user's home or profile directory by default, with no administrator privileges. Use dedicated directories for the app and its data so the fork can run alongside the official Minecraft Launcher, Prism, and PineconeMC on the same account.

| Platform | Default app location | Default data location |
| --- | --- | --- |
| Windows | `%LOCALAPPDATA%\Programs\CentralisedLauncher` | `%LOCALAPPDATA%\CentralisedLauncher` |
| macOS | `~/Applications/CentralisedLauncher.app` | `~/Library/Application Support/CentralisedLauncher` |

Use the dedicated data location for settings, instances and their game directories, downloads and caches, launcher-managed Java runtimes, logs, and backups. The app identifier is `io.github.unitduck.CentralisedLauncher`. Use that same identifier for the credential-store service when implementing pack publishing and subscriptions. First launch, upgrades, and uninstall must leave existing Minecraft and launcher directories alone. Verify this with an existing installation on both platforms. The macOS setup should create `~/Applications` if it does not exist.

## Player experience

1. Open the launcher and select **Subscribe to instance**. Paste the code and see the pack name, publisher fingerprint, and server details from the verified manifest. Confirm once that you trust this publisher to supply mods which run on your computer. A friend can confirm the fingerprint with the admin if they got the code somewhere unexpected.
2. Choose **Use a username**, **Sign in with Microsoft**, or **Sign in with Ely.by**. The username-only flow creates a local offline profile with no Microsoft or Ely.by sign-in in the launcher. Keep the chosen profile for later launches. The launcher should explain before launch when the chosen profile is incompatible with the advertised server setup.
3. On the first **Play**, show progress for installing Minecraft, Java if needed, the loader, mods, and configs. Start Minecraft once the install is ready. Add the group's server to the Multiplayer list so joining requires no address entry.
4. On later presses of **Play**, check for a published update. Install and verify it before starting the game. With no update, launch the installed version. If the check or update fails and a playable copy exists, show **Retry** and **Play installed version**, with a warning that the server may now expect a different version. On a failed first install, offer **Retry**.
5. Let players choose **Use recommended RAM** or set their own limit. Show the effective value. Let them stop subscribing while keeping the instance as an ordinary local instance, or explicitly remove it through the normal delete flow.

Pasting the same valid invitation again should select the existing subscription. After invite rotation, pasting a new code for the same pack and publisher should reconnect that instance in place, preserving its local data.

## Admin experience

1. Create or select a regular local instance. Choose the game, Fabric Loader, mods and dependencies, selected configs, recommended RAM, server name and address, and supported login mode. The normal upstream instance editor remains available for this work.
2. In **Pack publishing**, connect the separate distribution repo once. Use an admin-owned GitHub credential scoped to that repo. The launcher stores credentials and pack publishing keys in the system credential store. Keep a recovery copy of the publisher signing key and current pack key somewhere private, so the admin can resume publishing if they move machines.
3. Preview what will be shared before publishing. Show added, changed, and removed managed files, version and RAM changes, the server details, asset size, and any file that cannot be downloaded or shared. Let the admin review config contents for tokens, machine-specific values, and personal data.
4. Test the draft with the server. Publish with a short changelog, then copy the invite code. Later updates use the same code. Local edits remain private until the admin clicks **Publish update** and the upload is fully committed.
5. In **Pack history**, see the current release and the latest confirmed working backup. Use **Open backup instance** to recreate a separate local test instance from that snapshot. Use **Restore backup for everyone** to publish its contents again. After testing a published build against the server, the admin can mark it **Working**. Keep that release eligible as a fallback across subsequent unconfirmed releases.

## What the pack controls

| Item | First-release behavior |
| --- | --- |
| Minecraft and loader | Pin the exact Minecraft Java version and Fabric Loader version. Include any required Fabric API version as a separately pinned mod. |
| Mods and dependencies | Publish the exact client-side file list, including required dependencies. Prefer pinned downloads from the mod's authorized host. Bundle permitted files when a direct download is unavailable. Flag unshareable files during preflight. |
| Config | Manage only paths explicitly selected during publishing, primarily under `config/`. Treat each listed path as a whole managed file. Save a recoverable copy if a local edit is about to be replaced or removed. Unlisted configs stay local, including configs generated by mods after launch. |
| Server entry | Seed the Multiplayer list and update only the entry the launcher added while it still matches the previously seeded values. Preserve the player's other entries and any edits they made to the seeded entry. If needed, offer to add the updated address as a separate entry. |
| RAM | Publish a recommended maximum in MiB. Use a machine-appropriate safe value when the recommendation is too high, surface any adjustment, and preserve a player's explicit override through updates and rollback. Validate the final value against the current machine and launcher limits. |
| Personal and machine-specific files | Keep saves, screenshots, accounts and tokens, keybinds, video settings, logs, local Java paths, and unrelated launcher settings on the player's device. Offer a local world backup before opening an existing save after an incompatible game or mod change. |

Use an explicit allowlist for export. Other paths, arbitrary JVM flags, commands, executable hooks, and account or service settings are outside the publishing format. On a subscribed instance, detect local extra mod JARs before launch and offer to move them to a local holding folder or to make a separate editable copy. The launcher should never silently delete those files. Sync may remove a formerly managed file only from a path recorded in that instance's previous managed inventory. If a newly managed path would overwrite a previously untracked local file, retain a recoverable copy first.

Publish pack metadata, approved mods, and selected configs. Fetch Minecraft and its libraries through authorized upstream sources and obtain loaders and mods from their supported sources. Never redistribute Minecraft client or server binaries as pack files. A non-redistributable mod with no authorized automatic download needs a replacement or an explicitly supported install method before this one-click pack can ship. [Minecraft EULA](https://www.minecraft.net/en-us/eula) · [Fabric mod compatibility guide](https://docs.fabricmc.net/players/installing-mods) · [Modrinth file and dependency metadata](https://docs.modrinth.com/api/operations/getdependencies/)

## Login and the Minecraft server

The pack invite grants access to pack updates. Access to the game server is decided separately by its operator. Username-only play depends on upstream offline profiles and a server configured to accept them. A standard Microsoft-authenticated server requires a valid Microsoft session. Ely.by multiplayer requires a compatible server setup. Confirm in a real join test which paths work with the group's chosen configuration. Optional account sign-in alone does not authenticate a player to a username-only server.

For username-only multiplayer, use a trusted private network with server access limited to the people in the group. A username and a Minecraft whitelist alone cannot prove who is connecting. Plan to keep the same username and authentication mode throughout the phase. Switching identity mode can give the same player a different server UUID and can affect inventory, permissions, and progress. Test this before changing how an existing server authenticates players. Game installations should come from authorized sources and be used with authorized copies. [PineconeMC offline profile and account support](https://elyprismlauncher.github.io/) · [Minecraft EULA](https://www.minecraft.net/en-us/eula)

If the account holder also operates the server, those still are two jobs. Publishing a pack does not deploy to the server or back up its world. Coordinate client releases with server changes, and keep a server-side world and configuration backup before game or mod upgrades where compatibility may change.

## Proposed $0 hosting and invite design

Use a dedicated public GitHub repository under the admin's control with a default branch and no backend service. The launcher retrieves a small current-release record from the repo and downloads the versioned encrypted pack asset from GitHub Releases. Use explicit release asset IDs or versioned paths. The newest item in GitHub's release listing is not the publication signal. GitHub currently documents a size limit of under 2 GiB per release asset. Keep the pack small with pinned upstream downloads and observe GitHub's rate limits for anonymous reads. [About GitHub Releases](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases) · [Release assets API](https://docs.github.com/en/rest/releases/assets) · [GitHub REST rate limits](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)

- An invite is one pasteable string. It carries a format version, GitHub owner and repository, stable pack ID, current key generation, strong random read key, and the publisher's signing public key. It may be longer than a manually typed PIN. No GitHub login is required for a subscriber.
- Encrypt the manifest and bundled content before upload with a standard authenticated-encryption library. Use a fresh nonce per object with the required library and algorithm guarantees. Sign the release record with the publisher's private key, and bind it to the pack ID, key generation, revision, asset identity, and expected digest. Verify against the public key pinned by the original invite. The signing key establishes the publisher and the read key gives access to the content. Use an established signature implementation, such as Ed25519, and define the exact signed bytes and encryption envelope before releasing clients.
- GitHub visitors can see the repository, opaque release identifiers, timestamps, and approximate sizes. Keep pack names, server addresses, changelogs, configs, and code secrets out of public filenames, git commits, and release descriptions. Credentials and invite keys stay out of logs and crash reports. Restrict the admin's GitHub token to the distribution repository with the permissions required to manage releases and update the current record. [GitHub repository Contents API](https://docs.github.com/en/rest/repos/contents) · [GitHub Releases API](https://docs.github.com/en/rest/releases/releases)
- Anyone who gets a working invite can use or share it. If it leaks, the admin rotates the read key, republishes under the new key, and sends a replacement code to the group. The stable pack ID and signing identity let players reconnect the existing instance. Old codes cannot decrypt updates under the new key. Files already accessible or downloaded with an old code can still be copied. The launcher should show **New invite required** when a signed release announces a newer key generation.
- Keep the publisher signing key backed up separately from the repo. If it is lost or compromised, replace the publisher identity and have friends explicitly reconfirm a new invitation. Never accept a surprise signing key change during an ordinary update.

## Publish and install protocol

### Release records

- **Invite record** identifies the source, pack, and trust keys. A validated pack ID and normalized GitHub repository locator determine where the client reads from. Do not treat pasted codes as arbitrary URLs.
- **Current-release record** contains the schema version, pack ID, key generation, monotonically increasing publication revision, and encrypted asset locator, size and SHA-256, plus the publisher signature. Include a timestamp for display or diagnostics. Order by revision rather than by a client's clock.
- **Encrypted pack** contains a manifest and the approved bundled files. The manifest repeats the pack ID and publication revision and records the pack name, changelog, exact game and loader versions, RAM recommendation, preferred server entry and login mode, and the full desired inventory. Each managed file has a relative path, size, SHA-256, and either a bundled entry or a pinned upstream download. A restore can record which earlier revision supplied its contents.
- **Local subscription record** keeps the trust identity, current key reference, last verified publication revision, last successfully installed revision, previous managed inventory, and the player's overrides. Track the highest verified revision independently from the installed version so a failed download can retry the same newer revision while stale metadata cannot downgrade the instance. If the same revision appears with different signed content, stop and report a publish conflict.

### Publish

1. Freeze and validate the selected source files against the preview. Build and verify the manifest and encrypted asset locally. Compute all hashes over the exact bytes they describe.
2. Upload under a unique release and asset name, verify the uploaded asset, then update the current-release record as the final step. Use the file SHA read at the start of the publication when replacing that GitHub record. The first publish creates the record only if it is still absent. On a conflict, stop, reload it, and let the admin retry.
3. If the pointer update times out, reread it before retrying. An upload that never became current must not affect installs. An unused asset can be cleaned up later after confirming it is not referenced by a current, backup, or staged release. Keep published assets referenced by retained records intact. Use clear success and failure states in the launcher.

### Check, install, and recover

1. Check synchronously at **Play**, with a bounded network timeout. Use conditional requests where supported and honor any rate-limit backoff. Show which revision is installed and whether the check succeeded. During an outage or stale response, the player can explicitly launch a known usable local copy. A later **Retry** or **Play** checks again.
2. Verify the record before fetching its asset. Reject invalid signatures, unexpected pack IDs, stale revisions, unsupported schema versions, oversized payloads, and changed digests. Check the archive and each downloaded file against the manifest before installing. Limit file count and expanded size. Reject absolute paths, traversal, symlinks, reserved device names, and path collisions on case-insensitive Windows and macOS filesystems. Restrict download destinations and redirects to supported HTTPS sources without forwarding credentials across hosts.
3. Plan changes against the current managed inventory. Reuse verified unchanged files and cached downloads. Require enough disk space for staging and recovery. Stage under the same filesystem as the live instance and reuse the upstream Minecraft and Java installation mechanisms. Take a per-instance lock and wait for Minecraft to exit before applying changes.
4. Retain recoverable copies of files the update changes. Use a transaction journal and filesystem renames where supported so an interruption can finish the commit or restore the previous usable state. Commit the new managed inventory and installed revision only after the matching files are in place. Recover incomplete transactions on the next launch. Recheck managed-file drift before launching and offer repair if required.
5. Start Minecraft using the chosen profile and effective RAM. Report game launch failures separately from download or install errors. When a previous usable managed snapshot is available after a broken launch, offer to use it without changing the subscription or overwriting personal files. The next normal **Play** checks the published revision again. Launching a previous version may require restoring a separately backed-up world if the player has already opened an incompatible save.

## Backup and rollback

- Keep an exact snapshot of the latest confirmed working pack, including its manifest, approved bundled content, pinned references, and recommended settings. Keep the snapshot locally in the admin's pack history and keep the corresponding encrypted assets on GitHub. A backup shields the pack state itself. Test that pinned third-party downloads are still available, and retain lawful local copies of permitted dependencies if needed for recovery.
- **Open backup instance** makes a new local instance so the admin can check the last working setup without touching the current draft. **Restore backup for everyone** republishes the backed-up content as a new, higher revision under the active key. Existing invitations continue to work unless the key was rotated. Clients apply the rollback at their next update check, including those that skipped the broken release. A broken publish must not erase the backup.
- If the server was upgraded too, restore its compatible mods and server configuration, and use an appropriate server world backup when a downgrade needs one. The launcher pack restore does not roll back the server or a player's save. Tell the group when the server is ready so they know when to start the restored pack.

## Build order and release checks

1. Pin upstream and build it for Windows and the group's macOS architecture or architectures. Verify username-only offline profiles and optional upstream sign-ins. Test a real private server join. Test the installation experience on clean accounts. For the $0 Mac build, document the first-open experience for the trusted group and verify it on their machines. Apple explains when macOS permits a user to approve an unnotarized app. [Apple's Gatekeeper guidance](https://support.apple.com/en-us/102445)
2. Implement managed export, the manifest format, and local install from a fixture pack. Verify exact game and loader resolution, mod dependency changes, config ownership, server list seeding, RAM overrides, and preservation of personal data.
3. Add publishing and invite handling against a test distribution repo. Confirm that a friend with no GitHub account or token can subscribe. Confirm that an ordinary subscriber cannot publish, a leaked old invite cannot open releases under the new key after rotation, and a replacement code reconnects the same instance.
4. Verify two-player update and rollback across Windows and macOS. From a clean install, paste the code, choose a username, and join the server without copying any files. Publish an update that adds, changes, and removes managed files. Restore the confirmed working backup and verify the correct content for both a client that installed the bad release and one that skipped it.
5. Try a stale or unavailable feed, failed or partial upload, killed launcher mid-update, full disk, rate limiting, corrupted file, invalid invite, and an update while Minecraft is still running. Verify clear errors, a safe retry, and recovery of the last usable version. Verify that the invitation, keys, tokens, and local account data stay out of public assets and diagnostics.

The first release is ready for the friend group once those checks pass. Decisions to make at implementation kickoff are the distribution repo name, actual game and loader versions, mod list, Mac architectures, and how the group will reach the private Minecraft server. Per-person invitations, a hosting dashboard, background updating, automatic launcher self-updates, Linux builds, multiple publishers, and game-server deployment can wait.
